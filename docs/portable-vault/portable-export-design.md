## Implemented evidence

[Swift writer](../../spikes/cryptomator/Sources/WagLockPortableExportFixture/Fixture.swift) builds a format-8 SIV_GCM candidate from generated bytes using pinned cryptolib-swift 2.0.0. It encrypts file names and contents, writes an encrypted completeness manifest, and places a **separate encrypted vault** inside the outer vault. An ordinary folder is not a separate password domain. Only after its manifest is complete is the candidate published from staging. This is a public-fixture generator, not a general-purpose current-library exporter.

The official, unmodified **Cryptomator CLI 0.6.1 mac-arm64** recovered it using a loopback WebDAV reader, without FUSE/system drivers. The downloaded release's code signature verified as Skymatic GmbH / team `YZQJQUHA3L`, and its ZIP SHA-256 was `9252f8765db5068931d78f1ee74f7fe4d653605bf691d30e05c119eb5fa5d0d3`. This records a reproducible test version, not a current security endorsement or distribution clearance.

The same writer also compiled for `arm64-apple-ios17.6-simulator`, ran under the disposable iOS 18.4 simulator, and produced a candidate recovered by the same independent desktop CLI. Both runs verified outer and inner byte hashes. The outer password failed to unlock the recovered inner vault. The inner password succeeded without the original writer's in-memory keys, original inner source directory or any Keychain input.

[The recovery harness](../../tools/verify_portable_export.py) verifies inventory, byte counts and SHA-256 values before publishing a recovered destination. Missing manifest, payload tampering and removal of a complete final data chunk all failed verified recovery and left no published/partial recovery folder. The initial eleven adversarial parser/recovery tests passed. The hardened helper now passes 24 recovery tests and seven migration tests (31 total); see the follow-up below. [Results](portable-export-experiment-results.json) distinguish macOS and iOS-simulator writers. No GUI app, Windows/Linux, physical iOS execution or current-library recovery was validated.

## Proposed production direction

1. **Export first, native alignment later.** Keep the installed readers, schema, secrets and credentials. Develop a separate format-8 export adapter only after the remaining readiness gates below. Do not replace native encryption just to make a copy operation simpler. Reassess native alignment after independent compatibility, integrity, recovery, performance, distribution and migration evidence.
2. **Snapshot the complete logical library.** Capture explicit record IDs/metadata under the originating owner context. Include originals, metadata, thumbnails, notes, albums and a declared Trash policy; never silently omit a category. Capture an inventory/consistency point and detect missing or changed sources. A database file copy alone is insufficient, especially with WALs and device-bound keys.
3. **Keep password domains.** Inherited albums can be ordinary directories inside their parent's encrypted domain. Independently password-protected albums become separate nested vaults, each with an independent random masterkey and its own password wrapper. Protect inner names/catalog/media with the inner domain; do not put usable inner keys in an outer-password-only manifest. Ancestors must still be accessible before opening a descendant.
4. **Collect the required export credentials explicitly.** An unlocked album secret or Face ID success does not reveal the user's original album password. Prompt for and verify each required distinct password, or design an explicit separate export-password choice. Face ID-only copies need a deliberate password-readable export/recovery path with clear disclosure, or a blocking unsupported-state message. Do not silently omit, weaken or change the installed album. Existing device-bound semantics remain intact until an accepted design handles this exception.
5. **Bound plaintext and publication.** Encrypt directly where a reviewed streaming adapter permits; otherwise use one protected, operation-owned temporary file at a time, never a whole plaintext snapshot. Recheck vault/session/album generations across each await and before publication. Background, logout, ancestor lock or cancelled export revokes the job. Failed cleanup retries only known owned paths. Publish a complete encrypted package atomically; preserve sources on interruption, low storage, uncertain saves and partial copies.
6. **Recover with an independent open-source implementation.** Supply pinned tested client/tool versions, prerequisites, separate-password instructions and a completeness verifier. Validate cold recovery and hashes on supported desktop platforms. Phone restore must separately rebuild a protected index and verify every record/content binding before replacing anything; the experiment does not implement that restoration path.

## Integrity contract that must be resolved before adoption

An encrypted manifest lists each file's relative path, expected plaintext byte count and SHA-256, plus directory inventory and nested vault roots. The manifest itself is an ordinary authenticated encrypted file, omitted from its own hash list. It must be present and parse as one supported bounded schema; missing, duplicate, traversal, extra/missing-inventory and malformed entries fail closed. This does not prevent replay of an older complete authentic snapshot without an external trusted anchor.

**The unmodified CLI accepts a valid 65,536-byte prefix when the final complete chunk is removed from the 65,573-byte fixture.** The manifest-verifying helper rejects that loss. An ordinary Cryptomator reader does not automatically enforce WagLock's manifest. Opening the vault successfully alone is therefore insufficient evidence of completeness. Native adoption must not silently weaken the current ZNSC v2 final-record check. Decide and validate app-side read verification and mandatory recovery verification before claiming equivalent completeness guarantees. The manifest is an experimental application layer, not a change to Cryptomator's standard format.

## Readiness gates still open

- Production dependency/license and App Store/TestFlight route under D2S-106. Downloaded tools and dependencies remain isolated research artifacts; no new package is linked to WagLock.
- Integrity/read contract above, bounded hostile key/config parsing and KDF resource limits. The Swift generator only reads its own fixtures; it is not a hardened importer.
- Complete current-library metadata/key capture; per-album password workflow; explicit Face ID-only export handling; Trash/notes coverage; consistent WAL/concurrency handling.
- Large real photo/video and long-name handling. The fixture writer rejects components over 120 UTF-8 bytes instead of implementing shortened-name layout. It buffers fixture bytes; bounded-memory production streaming, cancellation, disk-full, restart and transaction journaling remain unimplemented.
- Physical iOS and desktop platform matrix, app UI, cold restore of a real supported library and source-preserving migration/rollback rehearsal. A simulator executable is not an installed iOS app integration.

These are implementation gates, not evidence that the whole feature is ready. No destructive migration or beta distribution follows from this experiment.

## Recovery verifier hardening — 2026-10-22

D2S-114/110/116 follow-up. The former final `Path.rename` could replace an empty destination created by another process during recovery. A deterministic regression reproduces that failure against commit `a1a3270`. Publication now uses macOS `renamex_np` with `RENAME_EXCL`, verified against the installed SDK definition, and fails rather than replacing any existing entry. The regression checks empty directories, files and dangling symlinks by inode and content. Failure removes only this operation's staging folder.

Manifests now reject unsupported fields, missing/conflicting parents, case/Unicode-normalization aliases, invalid encodings and excess resources. The parser preserves valid Unicode names; it rejects collisions instead of silently renaming them. The 1,000-entry bound includes the manifest. WebDAV parsing rejects foreign authorities, duplicate/escaping paths, ambiguous encodings, unsupported XML declarations and failed/ambiguous property statuses. The official CLI omits file `resourcetype`; its successful bounded `getcontentlength` response is explicitly supported and tested. Both inventory and manifest are rechecked after payload verification before publication.

All 31 Python tests passed. The final helper independently recovered the existing macOS and iOS-simulator public fixtures with official CLI 0.6.1, preserving hash checks, outer/inner password separation and rejection of tampering, missing manifest and complete-final-chunk removal. See [machine-readable evidence](portable-export-recovery-hardening.json). An initial stricter property check rejected the CLI's legitimate response and was corrected from the public response before final validation.

This strengthens the experiment's recovery side; it is not a hardened Cryptomator configuration/KDF importer, production app export or acceptance of the format. Publication is validated only on macOS and deliberately fails on other platforms. Keep the destination parent trusted and private; no protection against an attacker running as the same OS user, concurrent replacement of staging/parent directories or crash-durable fsync transaction is established. Final rechecks detect tested changes; they do not replace an immutable source snapshot or prevent replay of a complete older authentic export. No new app dependency, phone build or live storage mutation was made.
