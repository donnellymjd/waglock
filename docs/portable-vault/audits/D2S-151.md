## What a hostile but knowledgeable encryption-community reviewer would say

> You should have traced every caller instead of treating a secure helper as a secure application. The album preview omitted the integrity binding that the main library already had. The audio importer omitted the selected vault that the Audio screen already passed. Your tests proved the helpers and still missed the dispatch boundaries.
>
> You should have used the same byte semantics everywhere a password is compared. A green confirmation indicator based on Swift's Unicode equivalence is wrong when the KDF consumes exact UTF-8. Test composed and decomposed text, not just ASCII examples.
>
> You should have treated a new authenticated format, encrypted index, rollback journal and independently implemented age writer as a substantial maintenance liability. Standard primitives do not make custom integration independently audited. Evaluate maintained formats/libraries and publish compatibility and negative-case evidence before claiming interoperability. Replacing storage hurriedly with Cryptomator would merely introduce another unaudited integration and migration risk.
>
> You should have called short PINs weak against offline extraction, even with stronger PBKDF2 and online throttling. A six-digit PIN has a million possibilities. Reusing it for an export carries that weakness into a portable file. A strength meter and Face ID cannot manufacture entropy.
>
> You should have said plainly that a decoy is a separate library, not forensic deniability. Public source, app behavior, backups, provider suggestions and OS artifacts may reveal it. Assigning Face ID can reveal whichever library owns the grant. UI discretion cannot protect against every coercer or a compromised device.
>
> You should have maintained one current readiness ledger. A README narrating old builds and pending fixes that are already accepted makes every other security claim harder to trust. Passing your own tests is useful; it is not a human cryptographic audit, complete physical-device coverage or authorization to ship.

The criticism above is a simulated AI perspective. The recommended immediate response is the small fixes below and accurate limits, not a last-minute crypto/storage replacement. A maintained-library and independent-review evaluation belongs on the post-launch security roadmap with compatibility and migration gates.

### Crypto reference checks

Selected age writer checks follow the [age v1 specification](https://github.com/C2SP/C2SP/blob/main/age.md): fresh payload nonce, domain-separated derivation, authenticated64KiB chunks with counter/final marker, scrypt parameters and stanza rules, and rejection of all-zero X25519 shared secrets. Existing official age1.3.2 recovery and damage/wrong-parent tests are [recorded here](../../release/evidence/prelaunch-2026-10-26/independent-recovery.json). This is selected interoperability/negative-case evidence, not conformance certification.

PasswordEnvelope's PBKDF2-HMAC-SHA256600,000 iteration policy aligns with the corresponding minimum in [OWASP's password storage guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html); memory-hard choices deserve future evaluation. This does not establish FIPS validation, strong entropy for short PINs, or universal device performance. Random salts/data secrets use platform randomness; protected biometric factors use Apple's passcode-set device-only Keychain class and current-biometry ACL. See [Apple's Keychain security model](https://support.apple.com/guide/security/keychain-data-protection-secb0694df1a/web); app integration still needs its own tests.
