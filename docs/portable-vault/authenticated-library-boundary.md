# Authenticated library boundary and legacy transition rehearsal — build 29

2026-10-21. [D2S-115](https://linear.app/d2sci/issue/D2S-115), D2S-105/111/116. Build 28 remains the last owner-accepted phone baseline. This change prepares the independent-vault boundary; **it does not deliver a second usable encrypted vault or convert the current library**.

## Production change

The app no longer constructs or mounts the legacy SwiftData database before authentication. `AuthenticatedLibraryView` mounts ContentView only after successful login. `LibraryMountCoordinator` receives the expected session ID and scope, opens the container, and checks authorization, cancellation and operation generation before publishing it. A logout, a new login or a mode change prevents an older open/error from replacing the new mounted library. The former scene-wide model-container environment has been removed.

Owner sessions retain the exact legacy schema and default persistent configuration: MediaItem, SecretNote and VaultAlbum, with the existing URL, schema migration behavior and app identity. Current presentation-only Guest Mode receives a fresh empty **in-memory** schema and cannot open the owner database through this mounting path. It remains Guest Mode, not the independent alternative vault: global file, settings, cache and biometric services are not yet comprehensively scoped. No claim of complete guest-service isolation follows from this change.

An open failure shows a generic Retry/Lock screen. It does not replace the library, reset credentials or fall back to a new persistent store. A fresh mount identity rebuilds the UI/query tree on reauthentication. Dropping a coordinator reference cannot forcibly close ModelContexts retained elsewhere or erase copies already returned; explicit service/session checks remain necessary.

Authentication now uses an attempt generation around asynchronous verification/data-key loading. Logout and backgrounding invalidate pending authentication. Late results, errors and cleanup cannot authenticate a previous owner session, replace a newer guest session, clear a newer login's progress or publish stale errors. Queued password setup is cancelled before credential creation if the user locks first. Normal password, calculator-disguise and biometric completion paths check their originating generation. Session-key replacement/clearing publishes a fresh library-session UUID. Existing passwords, data secrets, Keychain namespaces and biometric enrollment remain unchanged. The requested warning now precedes new Face ID enrollment. Keychain writes recheck authorization after biometric consent and before mutation; stale completion no longer deletes a shared account that could belong to a newer enrollment. Cancellation/revocation tests preserve a disposable existing credential. No actual Face ID enrollment is simulated or claimed by those tests.

## Disposable legacy-metadata rehearsal

`WagLockTests/Support/LegacyMetadataTransitionPrototype.swift` is compiled **only into tests**. It accepts explicitly supplied disposable snapshots, roots and keys. It has no production singleton, login routing, Keychain access or media conversion. It must not be pointed at the running app's database or real media.

The capture maps every current stored property of MediaItem, SecretNote and VaultAlbum, including raw type/protection values, Unicode names, dates, dimensions/duration, thumbnail bytes, note tags/favorites, parent IDs, biometric account references, wrapped album keys and encrypted album catalogs. The caller supplies the existing synthetic data secret; the rehearsal preserves it rather than generating a replacement for legacy ciphertext. Original encrypted media paths are retained as data, never followed or rewritten.

The experiment stages independently encrypted metadata records with random opaque filenames. A sealed manifest binds record identities and ciphertext SHA-256 digests; AES-GCM additional authenticated data binds the format version, library, vault, purpose and record filename. All staged records and the retained synthetic secret are read back and compared before directory-rename publication. Failures remove only the invocation's owned staging directory. A publisher that reports failure after completing the rename leaves the verified published copy intact.

The reader decrypts only the requested page of records; a 1,000-record test verifies a 32-record page decodes 32 records rather than the entire dataset. The manifest is still decoded as a whole, capture buffers its source, and all records are written for each snapshot. **This is an immutable transition experiment, not a scalable mutable production index.** It has no resume journal, concurrent-writer protection, trusted anti-rollback anchor, production key wrapper, media streaming, full recovery package or approved storage format. Encoded records are capped at 4 MiB and the manifest at 8 MiB/20,000 records; these are experiment limits, not product import caps. The bounded plaintext search is not a forensic audit. Symlink checks are sequential fixture protections, not descriptor-relative protection against a concurrently malicious filesystem. CryptoKit and caller-held copies cannot be guaranteed erased when the reader drops its key/manifest references.

## Read-only SQLite finding

The old-module fixture is a self-contained SQLite database whose header still indicates WAL mode. A direct `allowsSave: false` SwiftData open failed because no WAL sidecar existed. The successful test prepares **only a disposable clone** with SQLite `journal_mode=DELETE`, then opens that clone with saving disabled and verifies its bytes remain unchanged during capture. The bundled original fixture also remains unchanged. It does not modify a live database or establish a generic WAL-aware snapshot implementation.

A production exporter cannot copy only the main SQLite file while imports, note autosaves or other writers are active. It needs a coordinated, consistent snapshot including committed WAL state, and a plan that avoids creating unprotected plaintext metadata copies. Do not change a live library's journal mode, checkpoint it, create plaintext clones or delete sidecars based on the fixture workaround.

## Proposed next integration, requiring resolved design and evidence

1. Quiesce and revoke all legacy writer capabilities, including imports, recording, notes/autosave, albums and pending background work. Establish a consistent source snapshot with explicit schema/version gates and a tested WAL strategy.
2. Select and document a mutable encrypted-index design and crash/resume journal. The record/manifest experiment is evidence for field preservation and paged reads only. Cryptomator remains a proposal; no package or production format is adopted here.
3. Stage a distinct encrypted metadata destination; retain legacy media keys, paths and readers. Verify counts, every metadata field, album envelopes and streamed original-media hashes before activation. Preserve the original library and a verified rollback path. No automatic cleanup of unknown files or deletion of the sole source copy.
4. Introduce explicit vault/session contexts at every service boundary. Independent vaults require separate random secrets, credential wrappers, ciphertext/index roots, settings, album/biometric accounts, caches and asynchronous jobs. Reject foreign references and late operations at commit and publication, not just UI filters.
5. Wire the ordinary two-passcode router only after service-level isolation exists. Reject identical passcodes and retain generic failures. Existing Guest Mode credentials must not be silently repurposed as a new vault or overwrite primary credentials.
6. Implement the owner's 2026-10-21 Face ID decision: optional convenience assignable to either independent vault, one explicit target at a time. Enable/reassignment must show the target-disclosure warning; passcodes remain the way to choose a different vault. Target binding, credentials and management must be scoped without exposing another vault in the secondary UI. Do not silently disable or repoint existing enrollment. Build 29 adds the warning for the existing single vault, not the independent target router.
7. Validate two populated disposable vaults, physical-device lifecycle/biometrics, interrupted migration, cold restore and rollback before enabling sensitive data or claiming an alternative-vault feature. This makes no promise of forensic invisibility or coercion safety.
