# WagLock Repository Guidelines

## Fork Mission and Source of Truth
The working app/fork name is **WagLock**, with the tagline **We Always Guard**. This fork develops WagLock, a fully open-source, local-first encrypted photo/video gallery based on SealedPocket (formerly ZeroNet Space). It is not the official upstream app. Keep upstream attribution and license notices.

The phone-testing build is **WagLock Dev**, app ID `com.d2sci.vaultito.dev`. The owner requested WagLock identifiers on 2026-10-22: track the planned `com.d2sci.waglock.dev` replacement and corresponding test/release identifiers as an explicit identity/data migration before beta distribution; do not silently rename the installed identity or historical Keychain namespaces. Its Keychain service follows bundle identity and deliberately does not migrate upstream credentials. Read [device testing](docs/portable-vault/device-testing.md) before installing. Keep the existing app and its data separate; do not change this fork into an in-place upgrade without a migration plan. Local photo/file/gallery/audio imports are now unlimited by item count. The owner selected English-only beta UI on 2026-10-18; use Latin product/executable names, English messages and redacted English diagnostics. Preserve original notices and Unicode user data. See [beta readiness](docs/portable-vault/beta-readiness.md). Build 26 removes inherited VIP entitlements, audio-sharing/icon gates and StoreKit purchase code; do not reintroduce item caps or store prompts.

Read [the documentation index](docs/portable-vault/README.md), [requirements](docs/portable-vault/requirements.md), [architecture decisions](docs/portable-vault/decisions.md), and [D2S-105 audit](docs/portable-vault/audits/D2S-105.md) before architectural work. The linked Linear project and requirements are the product source; the checked-in snapshot records what was read on 2026-10-17. Update docs with relevant requirement/issue links when decisions change. Older README, DEVELOPMENT_GUIDE, CONTRIBUTING, privacy and store documents describe upstream behavior or historical plans; do not treat their claims as verified fork capabilities. ## Product and Security Guardrails
- Core local use must work offline without accounts, telemetry, subscriptions, referrals or arbitrary item caps. Storage is bounded by hardware; imports, audio export and alternate icons must not depend on purchase state.
- Native desktop-readable vaults remain a release goal. Build 39 adds an additional age backup with independent macOS extraction, subject to the documented coverage/resource/device-validation limits. **Cryptomator compatibility is a proposal pending D2S-106/107/109/110 validation. Do not replace the storage layer or convert existing libraries until technical, recovery, licensing and migration evidence supports an accepted decision.** Preserve legacy readers and original data; no assumed in-place conversion.
- Require a vault password independent of the device passcode. Vault Face ID is password-backed convenience. The user explicitly authorized **Face ID-only albums** on 2026-10-17; these require acknowledgement of device-bound loss risk and have no password/device-passcode bypass. Other album policies inherit parent protection, add a separate password, or allow password-or-Face-ID convenience. Read [album security](docs/portable-vault/albums-and-biometrics.md); always enforce ancestors, invalidate pending results on lock, and keep album media/metadata out of global gallery queries. The owner prioritized a secondary-passcode independent alternative vault on 2026-10-18 (D2S-115); follow [the proposed design and acceptance gates](docs/portable-vault/secondary-vault-design.md). Main and decoy vaults still need separate key/ciphertext/index domains; current Guest Mode merely hides content and must not be presented as the requested feature. The [two-vault prototype](docs/portable-vault/vault-isolation-prototype.md) is test-bundle-only; do not connect it to the existing library or treat it as an approved migration/storage format. Never promise forensic plausible deniability.
- The [mutable encrypted metadata candidate](docs/portable-vault/encrypted-metadata-candidate.md), typed model codec and resumable model-only stage have no production mount caller. A verified stage covers only its declared supplied records, not a complete live library; keep progress encrypted and atomic with its batch, bind the source fingerprint, and verify the saved prefix before resuming. Memory projections must remain memory-only. Preserve domain/purpose binding, opaque tokens, authenticated inventory, revision checks, revoked capabilities and uncertain-commit reconciliation. Never activate it against the legacy library without typed adapters, WAL-consistent staging, full verification and reviewed rollback/source-retirement evidence. Whole-copy rollback protection remains open; do not describe A01 as fixed.
- Encrypt sensitive metadata and thumbnails as well as originals. Stream large files; control plaintext preview/export lifetimes, cleanup after failure/cancellation/crash, and avoid sensitive logs. Treat SwiftData, WALs, caches, app-switcher snapshots and backups as part of the threat model.
- Build 23 streams use authenticated ZNSC v2 framing; preserve buffered/v1 readers and never silently convert a library. Read [stream integrity](docs/portable-vault/stream-integrity.md) for format details and residual v1 weaknesses. Keep destination publication atomic and test malformed/order/truncation cases before changing this code. Older builds cannot read v2 streams.
- Build 24 owner setup/password changes commit one authenticated Keychain record. Legacy login must remain read-only; never infer reset permission from preferences or Keychain errors. Preserve data keys, reject stale credential fallback, and generation-check cache publication across background/logout. Read [credential/cache hardening](docs/portable-vault/credential-and-cache-hardening.md). The [Cryptomator probe](spikes/cryptomator/README.md) is research only and must stay outside app dependencies; its completeness/desktop/licensing gates remain open.
- The [portable export experiment](docs/portable-vault/portable-export-design.md) now has independent official-CLI recovery of macOS/iOS-simulator fixtures, distinct nested passwords and manifest checks. It remains outside app dependencies and reads only generated samples. Standard Cryptomator reads do not enforce the extra completeness manifest; never claim native integrity equivalence or enable a live migration from this evidence alone.
- [Portable snapshot capture](docs/portable-vault/portable-export-snapshot.md) feeds the build 39 [age backup](docs/portable-vault/age-backup-design.md). Preserve supported-field inventory, original owner mount/session/revision checks across awaits, exact UTF-8 metadata and independent nested password domains. Locked content blocks capture. Face ID-only capture defaults to denial; only explicit per-album consent, real biometric authorization and a new confirmed export password allow a password-readable copy without changing native policy. Never serialize cross-domain plaintext snapshots or native keys/wrappers. Keep source readers/data unchanged, enforce streaming/metadata/disk bounds and reject unsupported content rather than omitting it. Only verified completed ciphertext may reach the native Files/cloud picker. Build40 permits a user-selected filename only through an exclusive rename inside the owned job; preserve suffix/path validation and never overwrite another file. Recovery verifies all requested domains before creating the readable Library layout; safe filename/collision handling and version2 archive-to-readable mapping must preserve original metadata and raw-layout compatibility. Read [independent recovery instructions and limits](docs/portable-vault/backup-recovery.md); do not equate provider acceptance with remote upload success or extraction with an in-app restore. Preserve BSD source/notices/provenance and require independent official age interoperability for format changes.
- Build 25 imports commit only to the originating owner session, after generation/session checks and database save. Preserve actually committed files on uncertain save outcomes; never turn this into a startup orphan-deletion scan. See [import lifecycle](docs/portable-vault/import-lifecycle.md). Use [disposable export fixtures](docs/portable-vault/migration-fidelity.md) for migration research; no real source exports or verified migration path exist yet.
- Build 32 export jobs require the authenticated owner session ID, snapshot metadata on the main actor and own separate protected temporary directories. Revoke exports on background/logout/key replacement. Cleanup is scoped to known jobs and retries owned failures; never revive global cancel/cleanup behavior or delete unknown media. See [export boundary](docs/portable-vault/export-session-boundary.md). This does not make Guest Mode an independent vault.
- Build 34 fixes the build 33 PDF logout crash: presentation and pager identity must use immutable metadata captured while mounted; never fault a live SwiftData record while its library is dismissing. Drive document resume from capability revision after the lock decision, and gate source-model actions by their originating session. See [document preview regression evidence](docs/portable-vault/document-preview-boundary.md).
- Build 33 common document previews use the revocable owner capability and per-view model in [document previews](docs/portable-vault/document-preview-boundary.md). Check both session and revision after awaiting; background/resume can retain the same session UUID. Keep generic QuickLook/media/audio gaps explicit.
- Private Photo Vault migration must preserve available originals, names, EXIF, dates, videos and albums, support verification/resume, and never automatically delete source assets or plaintext exports.
- Optional encrypted backup is disabled by default. Validate iCloud inclusion and cold restore experimentally. No two-way sync in the initial MVP.
- All existing features are free for the current beta. The earlier possible later upfront price is deferred; no VIP/paywall/entitlement flow is authorized. Do not gate owned offline vault access on payment status or referrals. Share without contacts uploads or incentivized reviews.
- Publish full release source, self-build/signing guidance, recovery instructions and evidence-backed limitations. Do not claim independent audit, byte-identical builds, or comparative security superiority without proof. Review GPL/AGPL, branding and App Store/TestFlight obligations before distribution; no new Cryptomator dependency is approved by this setup work.

## Project Structure & Module Organization
Core app code lives under `WagLock/`. `WagLockApp.swift` at that root is the SwiftUI entry point; `App/` holds app-wide constants. `Models/` defines SwiftData entities such as `MediaItem` and `SecretNote`, `Services/` encapsulates Keychain, encryption, storage, and import logic, and `ViewModels/` hosts the MVVM glue (`AuthenticationViewModel`, `GalleryViewModel`, `ImportViewModel`). Screens live under `Views/`, including authentication, gallery, import, audio, notes and settings. Shared utilities and UIKit bridges live in `Utilities/`. Tests sit in sibling `WagLockTests` (XCTest and Swift Testing) and `WagLockUITests` (XCTest UI flows). Assets reside in `WagLock/Assets.xcassets`; localized strings and plist inputs also live in `Resources/`.

## Build, Test, and Development Commands
- `open WagLock.xcodeproj` – launches the project in Xcode; preferred for day-to-day work.
- `xcodebuild -scheme "WagLock" -destination 'platform=iOS Simulator,name=iPhone 15' build` – CI-friendly build that validates SwiftUI targets.
- `xcodebuild test -scheme "WagLock" -destination 'platform=iOS Simulator,name=iPhone 15'` – runs both unit and UI test bundles. Use `-only-testing:WagLockTests` when iterating on business logic.

The app target currently requires iOS **17.6**, despite historical iOS 15 claims; Swift language mode is 5.0. Baseline inspection used Xcode 27.1 (27A9275). Discover available simulators with `xcrun simctl list devices available` and substitute an installed destination; do not assume iPhone 15 exists. Keychain tests need signing (local simulator ad-hoc signing is documented in BUILD_ERRORS_SUMMARY.md). An unsigned device compile can use `xcodebuild -project WagLock.xcodeproj -scheme WagLock -destination 'generic/platform=iOS' -derivedDataPath /tmp/portable-vault-build CODE_SIGNING_ALLOWED=NO build`; this is not device installation or runtime validation. Preserve signing/team/bundle/Keychain identifiers during audits. Build 28 renames source/test folders, project, scheme and Swift module to WagLock. Installed identity and data paths remain stable. Preserve historical Keychain service/account strings and cleanup aliases; see [branding and thumbnails](docs/portable-vault/waglock-branding-and-thumbnails.md) for database compatibility evidence.

## Coding Style & Naming Conventions
Follow standard Swift 5 conventions: four-space indentation, `UpperCamelCase` for types, `lowerCamelCase` for members, and `snake_case` for asset catalogs if required by iOS tooling. Keep SwiftUI views small and compose via extensions when modifiers exceed ~10 lines. Prefer protocol-oriented abstractions between services and view models and reuse helpers in `Utilities/`. Use Xcode's built-in formatter (`Ctrl+I`) before committing; no external linter is currently enforced.

## Testing Guidelines
Unit tests target encryption, Keychain, and import services in `WagLockTests` using XCTest; mirror the source file name plus `Tests` suffix (e.g., `EncryptionServiceTests`). UI workflows belong in `WagLockUITests` and should assert login, gallery browsing, and media import flows. Aim to keep encryption and password logic covered, and document any gaps in `BUILD_ERRORS_SUMMARY.md` when skipping a test.

Existing security coverage is incomplete; the preceding paragraph is guidance, not a coverage claim. For storage/security changes require meaningful wrong-password, tampering/truncation/order, key lifecycle, interrupted writes, disk-full, decoy isolation and recovery tests appropriate to the change. Use disposable fixtures and isolated Keychain services; never reset a user's vault. D2S-105 remains open until signed physical-device validation and its remaining acceptance work are recorded. Documentation-only changes need link/path checks and `git diff --check`; report build/test limitations honestly.

## Commit & Pull Request Guidelines
Commits follow short, imperative subjects (`Add session password storage`, `Fix photo picker crash`). Each commit should build and pass `xcodebuild test`. Pull requests must include: summary of behavior changes, linked issue or requirement doc, screenshots/video for UI adjustments, and a checklist confirming migrations or new assets. Highlight any security-sensitive changes (encryption tweaks, password handling) so reviewers can focus on regression risk.
